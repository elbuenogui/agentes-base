## Objetivo
Deixar a gravação mais robusta e com visibilidade de custo: configurações avançadas (microfone),
proteção contra gravação infinita, feedback visual, correção da permissão de microfone repetida,
painel de consumo (tokens/custo, sessão e histórico diário com gráfico) e a opção de testar
streaming no transcript.

## Escopo
- Dentro:
  - servir o frontend via servidor HTTP local (o backend passa a servir os arquivos estáticos),
    corrigindo a permissão de microfone repetida (origem estável em vez de `file://`);
  - ícone de configurações (estilo "avançado") ao lado do botão redondo, abrindo um popover/
    modal com o seletor de dispositivo de microfone (opcional, não obrigatório no fluxo
    principal);
  - cronômetro visível durante a gravação;
  - corte automático de segurança aos 2min30s de gravação, com aviso claro e envio automático do
    que foi gravado até ali;
  - barras de nível de áudio (visualizador simples) reagindo ao volume captado durante a
    gravação, reaproveitadas também para validar se houve áudio real captado antes de enviar
    para transcrição (evitar mandar gravação em silêncio/vazia, que a API às vezes "alucina" em
    outro idioma em vez de reconhecer como vazio);
  - registro de consumo no backend por requisição, usando o campo `usage` que a própria resposta
    da API já traz (tokens de entrada/saída; se vier no formato de duração em vez de tokens,
    calcular pela duração × preço por minuto como alternativa) — persistido num arquivo local
    (solução temporária; troca por banco de dados de verdade fica para depois, backlog);
  - novo endpoint no backend para consultar o consumo agregado (sessão atual e histórico diário);
  - ícone no mesmo estilo do de configurações, abrindo um popover/modal com o consumo da sessão
    atual, o histórico diário e um gráfico de custo por dia; botão de reset que zera só a
    visualização da sessão (o histórico salvo em disco continua intacto);
  - alternador de streaming (mesmo estilo do alternador de modelo) ligando/desligando
    `stream=true` na transcrição; com streaming ligado, o texto aparece incrementalmente na área
    de transcript.
- Fora (explícito):
  - banco de dados de verdade (o arquivo local é solução temporária, ver Backlog);
  - qualquer mudança na forma de cobrança ou otimização de custo — o objetivo é só medir e
    mostrar;
  - tornar a seleção de dispositivo de microfone obrigatória — continua opcional/avançada;
  - reativar o modelo diarize;
  - validação de qualidade/conteúdo da fala além de "teve áudio ou não" (ex.: detectar idioma,
    filtrar ruído) — só o mínimo de detectar se houve som captado.

## Etapas
1. [Servir frontend via servidor local] — Status: **concluída** (2026-08-18). Verificado no
   artefato real pelo PM: `transcritor/backend/main.py` importa `StaticFiles` e monta
   `app.mount("/", StaticFiles(..., html=True))` depois da rota `POST /transcrever` (sem
   colisão); `transcritor/README.md` orienta abrir `http://127.0.0.1:8000/`, com nota sobre
   `file://` ainda funcionar mas pedir permissão toda vez.
2. [Painel de configurações com seletor de microfone] — Status: **concluída** (2026-08-18).
   Verificado no artefato real pelo PM: `#botaoConfiguracoes` (classe `.icone-avancado`,
   reaproveitável pelo ícone de consumo) abre um modal com `select#dispositivoAudio`; a escolha
   é guardada em `dispositivoEscolhido` e usada como `deviceId` na gravação seguinte (confirmado
   no código, `restricoesAudio = dispositivoEscolhido ? {deviceId:{exact:...}} : true`); sem
   escolha, continua usando o padrão.
3. [Cronômetro + corte de segurança] — Status: **concluída** (2026-08-18). Verificado no
   artefato real pelo PM: `#cronometroGravacaoRapida` mostra mm:ss; `LIMITE_GRAVACAO_MS = 150000`
   (2min30s) agenda `cortarPorSegurancaGravacaoRapida()`, que usa o mesmo caminho de parada do
   clique manual; `pararTemporizadoresGravacaoRapida()` cancela ambos os temporizadores em
   qualquer parada, evitando o corte disparar depois de uma parada manual. Executor testou de
   ponta a ponta com tempo real (sem acelerar relógio), confirmando o corte exato aos 150s.
4. [Barras de nível de áudio + validação de áudio real] — Status: **concluída** (2026-08-18).
   Verificado no artefato real pelo PM: `#barrasNivel` (12 barras) reage ao RMS do
   `AnalyserNode` conectado ao mesmo `MediaStream` da gravação; `picoVolumeRapido` acumula o
   maior pico da gravação inteira; `LIMIAR_SILENCIO = 0.02` decide, no `stop` do
   `MediaRecorder`, se envia ou mostra `mostrarToastSemFala()` ("Não foi identificado nenhuma
   fala"). Executor testou com áudio real via fake-audio-device do Chrome (arquivo `.wav` de
   silêncio e de tom simulando fala), confirmando os dois caminhos de ponta a ponta, incluindo
   checagem via CDP de que nenhuma requisição é disparada no caso de silêncio.
5. [Registro de consumo no backend] — Status: **concluída** (2026-08-18). Verificado no artefato
   real pelo PM: `transcritor/backend/main.py` tem `_registrar_consumo`/`_calcular_custo_usd`, o
   contador em memória `_consumo_sessao` e o endpoint `GET /consumo` (registrado antes do mount
   de `StaticFiles`, sem colisão); `transcritor/consumo.jsonl` existe em disco; CORS
   `allow_methods` ampliado para incluir `GET`; `transcritor/README.md` documenta o endpoint com
   exemplo real de resposta. `PROGRESSO.md` registra teste com três transcrições reais (dois
   modelos), custo batendo exatamente com o `usage` devolvido pela API nas três.
6. [Painel de consumo no frontend] — Status: **concluída** (2026-08-19). A pendência de
   validação real (implementação original testada só com mock) foi resolvida de passagem durante
   os testes da Etapa 7: `#botaoConsumo` aberto contra o backend real, mostrando dados reais
   gerados pelas próprias transcrições de teste daquela etapa (registrado em PROGRESSO.md, seção
   "Regressão — configurações, consumo, alternador de modelo" da Etapa 7).
7. [Streaming do transcript] — Status: **concluída** (2026-08-19). Verificado no artefato real

## Backlog (não aprovado)
- CORS do backend está aberto (`allow_origins=["*"]`), aceitável para uso 100% local — revisar
  se um dia o projeto for servido fora da máquina do usuário;
- trocar o arquivo local de consumo por um banco de dados de verdade — decisão explícita do
  usuário em 2026-08-18 de adiar essa troca para depois;
- histórico, armazenamento por projeto/entrevista, exportação, metadados;
- pipeline de limpeza → segmentação → classificação → resumo com modelos especializados;
- banco de dados, busca semântica, embeddings, RAG, corpus de entrevistas;
- camada de agente que decide qual modelo/informação usar;
- suporte a celular e smartwatch;
- transcrição em tempo real (diferente do streaming da Etapa 7, que é sobre a exibição do texto
  já gravado, não sobre transcrever enquanto ainda está falando);
- explorar plataforma de chat self-hosted tipo Claude com agentes/skills (Open WebUI, LibreChat,
  AnythingLLM, Dify, LobeHub) como possível motor para uma fase futura — discutido em
  2026-08-18, decisão de continuar em outro chat, nenhuma ação tomada neste projeto ainda;
  - efeito de streaming imperceptível em áudios curtos (a API responde rápido demais pro texto
    "aparecer aos poucos" ser visível) — comportamento inerente à API, não um bug (confirmado
    pelo Executor em 2026-08-19, cronometrado); item novo: se o usuário quiser o efeito visível
    mesmo em áudios curtos, precisaria de um adiantamento artificial de exibição (revelar o texto
    num ritmo mínimo, independente de quando o pedaço chegou da API) — mudança de escopo
    deliberada, decisão pendente do usuário.
